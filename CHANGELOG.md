# Changelog

All notable changes to MimirSynth. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project adheres to [Semantic Versioning](https://semver.org/) (0.x: the API and the schema may change between minor versions).

Releases publish a container image to `ghcr.io/mimirsynth/mimirsynth` (tags `X.Y.Z`, `X.Y`, `X` and `latest`; `linux/amd64` and `linux/arm64`).

## [Unreleased]
### Added
- **Import a brain** (#136). A package made with Export a brain becomes a new brain, from this instance or another one: in full, or only its structure (ontology and aliases) as a template. The package is uploaded in parts and read in full before anything is written: only regular files on the paths an export writes (no `..`, absolute paths or links), each with the size and `sha256` of a manifest of a known format version, plain label and relation names, relations that join nodes of the package, and counts that match. The graph goes in through its dump when FalkorDB's graph module has the exporter's version, and otherwise through its JSON copy with Graphiti's indices; under another slug, `group_id` is rewritten. The vectors are reused with the same embedding model and computed again with another one (graph, episode index and documents). The importer is the owner; folder and wiki sources come disabled and without their credentials, and an approved proposal that was not yet ingested goes back to pending. Any failure removes everything the import created, and an import cut by a restart is undone on the next start; a wrong password keeps the package uploaded to try another. If the brain has reference queries, they run once it is imported. It needs the instance administrator, runs as a job and is audited (`brain.import`, `brain.import.done`); the largest package is `MIMIRSYNTH_IMPORT_MAX_MB` (20,480). Administration → Brain access → Import a brain, and `/api/brain-imports`. See «Import a brain» in the wiki.

## [0.9.0] - 2026-10-31
### Added
- **Correcting facts from agents** (#109). A new kind of proposal, the **correction**, points to a fact by its uuid and asks to invalidate it, with a reason and optionally the text that replaces it: `POST /api/brains/{slug}/proposals/corrections` and the MCP tool `correct` (contributor role). It goes through the same quarantine, the decider never approves it on its own and over MCP it always waits for a person, even with a curator token; Proposals marks it and shows the fact as it was, the reason and the replacement. On approval the fact is invalidated (never deleted) as of the given date, the replacement is ingested with that date, and the invalidation goes to the vocabulary history like those from Facts and Contradictions. **Reactivate the fact** in the proposal undoes it. Facts that do not exist, are already invalidated or are lent by another brain return a readable error. Migration `0027`. See «Correct» in `docs/AGENTS.md`.
- **MCP tools to dig deeper** (#108). Besides `recall` and `remember`, the MCP server offers four read-only tools for reader tokens: `facts_about` (everything known about an entity, with dates, where each fact was learned and its uuid), `timeline` (when each fact was learned and when it stopped being true), `get_document` (a passage with the text around it, using the `[doc N, chunk M]` numbers from `recall`, or the full text in parts) and `whats_new` (facts learned and invalidated since a date, or since the last time the same token asked). Entities are found by name regardless of case and spacing, by merged names or by uuid, and an ambiguous name returns the candidates. Every answer has a size limit and pagination, and what other brains lend comes labelled with its origin. Migration `0026` (each token remembers its last `whats_new`). See «MCP server» in `docs/AGENTS.md`.
- **Contradictions between current facts** (#113). A relation type can be marked as single-valued in the ontology («A single value at a time»); Vocabulary → **Contradictions** then lists current facts with the same subject and relation and different targets of the same entity type, suggests keeping the one with the newest validity date (no suggestion when only learning dates are known), and resolving invalidates the others with its date (undoable from the vocabulary history). No AI model is used. **Measure across all relations** counts the candidates of every relation without changing anything, also from the command line (`python -m mimirsynth.conflicts <graph>`), so relations can be measured before being marked. A daily check raises the new `conflicts.found` alert (information). No relation is single-valued by default, not even in the packages: each brain marks its own after measuring. See «Single-valued relations and contradictions» in `docs/ONTOLOGY.md`.
- **Secret detector for proposals and documents** (#116). Before a proposal is stored (interface, API or `remember` over MCP) or a document is indexed, credentials are looked for: certain formats (cloud and AI provider keys, GitHub, GitLab, Slack, npm and Hugging Face tokens, PEM private keys, JWTs, `Authorization` headers, passwords in URLs…) and possible ones (a random-looking value assigned to `password`, `secret` or `token`). Each brain chooses, under Administration → Brain access → Secrets, to **mask** them (the default: certain ones become `[secret removed: type]`), **block** them (the proposal is rejected with a 422 saying which type it is; the document is not indexed) or **only warn**; possible ones are always only flagged, and a flagged proposal always waits for a curator's review, even when a curator sends it. A per-brain exception list turns rules off or accepts values, and **Scan what is already stored** runs the detector read-only over the brain's proposals and documents to measure hits and false positives. The value is never stored in the audit log, the logs or the API responses. The downloadable original of a document is not modified. Migration `0023`. See «Secrets» in `docs/ARCHITECTURE.md`.
- **Duplicate documents are detected and not indexed twice** (#117). Folder and wiki sources did not check whether a document repeated another, so the same note could end up indexed twice. Now a document whose extracted text matches one already indexed in the brain (ignoring case and spacing) is marked **duplicate**: it is neither chunked nor embedded, and Knowledge shows it with its own status filter and a link to the original. If the original is deleted, leaves its source, changes or cannot be indexed, the oldest duplicate is indexed in its place. **Find duplicates** in Knowledge (brain administrators) checks the documents indexed before this change and takes the repeated ones out of the index; nothing is deleted at the source. When two copies are indexed at the same time, or an older one is reindexed, the oldest always wins. Find duplicates runs as a job with progress. Migration `0024` (the fingerprint is an indexed column).
- **Reference queries to measure recall quality** (#115). Each brain can keep questions with what their recall must bring and what it must not (Ask → Reference queries, for curators and above). **Run** counts expected items found, false positives and queries with the documents section the wrong way round, with latency and the difference from the previous run; **Simulate** repeats it with other passage similarity thresholds without changing the setting. Queries are created by hand, imported and exported as JSON, or saved from Ask by marking results as «Expected» or «Extra»; Ask now also lists the document passages it returned. The comparison only counts what is in both runs (the same queries and texts), so adding or deleting queries never shows up as worse. During an embedding model change they run on their own before (as the baseline) and after it, and the new `refquery.regressed` event warns if they get worse, or says there was nothing to compare with. The last 20 runs per brain are kept, and query texts go through the secret detector. Migration `0025`. See «Reference queries» in `docs/ARCHITECTURE.md`.
- **Entity page** (#127). Everything known about one entity and how it changed, on one page (`/entidad/{uuid}`): its facts grouped by relation and read as an evolution («runs on: Eridani → Polaris → Notus»), with the earlier values folded and struck through with the period in which they were true; both the validity date and the learning date of each fact; related entities, the episodes and documents that mention it, and the curator actions (invalidate or reactivate a fact, links to merge, retype and edit). **As it was on** shows what was current on a given day, and a single-valued relation with two current values is flagged with a link to Contradictions. Generic relations such as `RELATES_TO` are folded into one «Other relations» section at the end. It is reached from Facts, the Graph («View page»), Cypher query and Ask, and a lent entity opens read-only with its origin. The API is `GET /api/brains/{slug}/entities/{uuid}` (`as_of`, `origin`) and `GET /entities?q=`. The Journal opens an episode from a link (`?episodio=`). See «Entity page» in the wiki.
- **Export a brain** (#130). One brain, without touching the others, in a `.tar.gz` package with a versioned `manifest.json` (MimirSynth and FalkorDB versions, embedding model, counts and every file with its `sha256`): the graph's `DUMP` and the same graph as JSON for another FalkorDB version, the ontology, aliases and vocabulary history, the proposals with their review, the documents (sources without their secrets, metadata, normalized text and originals) and the reference queries; the vectors of the search index only on request. Members, API tokens, AI engines, notification channels, federation grants, jobs and graph snapshots never go in. Everything goes through the secret detector first, whatever the brain's policy: a certain secret is masked, a graph with one goes without its dump, and a document goes without its original when it had one or was never checked. Optional **encryption** with a password (AES-256-GCM in chunks, key from scrypt; `python -m mimirsynth.packcrypt decrypt` opens it outside the app). The password only lives in memory until the job starts, so an export cut by a restart fails saying to export again. It needs brain administrator, runs as a job, is audited (`brain.export`, `brain.export.download`), can be downloaded once and expires after `MIMIRSYNTH_EXPORT_TTL_HOURS` (24). Administration → Brain access → Export, and `POST/GET /api/brains/{slug}/exports`, `GET …/exports/{id}/download`. Importing is #136. See «Export a brain» in the wiki.

### Changed
- **The author learns what the secret detector did** (feedback on #116). A curator's proposal with a certain secret is masked and approved at once, and nothing said so, so its author thought the detector had not worked. Now the form says which types were masked or flagged, `POST /proposals` returns the same text in `secrets_notice`, the `remember` result over MCP adds it, and the proposals list marks those proposals (**Secret masked** or **Secret to review**). The value is never in any of them.
- **Contradictions are easier to read and act on** (feedback on #113). A note at the top says what the tab is for and what each action does. The cases are a compact table (subject, relation, target type, number of facts, suggestion); **Review** opens a group, where the person picks the fact that is still true and presses **Resolve**, or **Not a contradiction** to hide a false positive until a new fact joins the group (listed under «Marked as not a contradiction», with **Show again**). Long facts are cut with **Show all**, and a long group scrolls inside its own area. Generic relations such as `RELATES_TO` are never compared and cannot be marked as single-valued. The Ontology relations table has a **Single value** column, the empty state links to measuring and to Ontology, and the measurement table can **Mark** a relation. Migration `0028`.
- **Contradictions: invalidate only the facts that are no longer true** (feedback on #150). A group could only be resolved by keeping one fact and invalidating all the others, so a relation marked single-valued by mistake («CheckMK MONITORS», 8 targets, one stale) was one click away from invalidating 7 true facts. An open group now has two modes, **Keep only one** and **Invalidate the ones that are no longer true** (a tick per fact, **Invalidate selected (N)**); one fact always stays current (the server refuses otherwise) and invalidating more than one asks first. A relation where some subject has 3 or more current targets, or a quarter of the subjects have several, is flagged as **probably several values**: its groups get no preselected fact, an open group warns and links to the relation's edit dialog in Ontology or unmarks it right there, and the measurement table shows the flag. `POST /conflicts/resolve` takes `keep` as optional.
- **Corrections stand out in Proposals** (feedback on #109). A correction only differed by its «Correction:» title prefix. The list now has a **#** column and a **Kind** column with an **Adds** or **Corrects** marker (icon and word, filled for corrections, also in the detail header), a **Kind** selector next to the state tabs, and a notice with the number of pending corrections and a shortcut to them. `GET /proposals` takes `kind` and sorts by `id`; `GET /proposals/counts` takes `kind` and returns `kinds` and `corrections_pending`.
- **Query screen: graph drawn on our own canvas** (#95, phase 6). The graph tab of the Query screen uses the same canvas as the Graph screen, with hover tooltip, focus on click and dashed invalidated facts, and follows the **Graphic effects** chosen on the Graph screen for this device. `@falkordb/canvas` and its dependencies are gone, so the main bundle is about 165 kB smaller (1,313 → 1,147 kB before compression).

### Fixed
- **Recall: duplicate document passages no longer use up the budget** (#65). When the same text appears in two documents (for instance the same note in two sources), or in the brain and in a source that lends its documents, only the first copy is kept, so the passages in a recall (2 by default) are the best *different* ones.

## [0.8.0] - 2026-10-30
### Added
- **Graph screen: radial, tree and 3D on our own renderer** (#95, phase 5). The Graph screen no longer uses `@falkordb/canvas` (the Query screen still does). Radial and tree are laid out as before (rings by level, parents centred over their children) and a layout change moves every node to its new place; dragging a node there leaves it where it is dropped. **3D** is drawn with WebGL (three.js and d3-force-3d), loaded only when 3D is chosen, and keeps what 2D has: the **Group by** selector, the **Origins** legend with each halo turned on or off, **Only confirmed by 2 or more origins**, focus, tooltip, particles, expansion and the graphic effects. In 3D a halo is a **translucent volume** around its nodes, more opaque at its outline than inside so that the nodes in it stay visible, with its name above it; halos are drawn only in the force layout, in 2D and in 3D. Without a GPU, **Reduced** in 3D also draws simpler spheres (about 40 → 57 fps turning a 115-node graph with 9 halos under software rendering), and if 3D is still slow a notice offers to go back to 2D. Nothing is drawn at rest in 3D either.
- **Graph screen: animations and graphic effects** (#95, phase 4). New nodes fade and grow in; hovering a node highlights its neighbourhood and dims the rest, halos included, shows a tooltip (name, type, connections and origins) and runs particles along its valid edges; above 60 visible nodes a **minimap** shows the whole graph and the current view, and a click on it centres the view there; a «Computing the graph…» overlay covers the canvas while it loads. Nothing is animated at rest: particles run only while a node is hovered and every animation stops on its own. A **Graphic effects** setting (Automatic, the default; Full; Reduced) is stored **per device** in the browser, not in the account, because the GPU belongs to the device: Automatic drops to Reduced by itself after about two seconds of slow frames (under ~30 fps) and says so in the selector. Reduced keeps the halos and drops the entry animation, the particles and the minimap, with fewer texts per frame (60 instead of 120). With `prefers-reduced-motion`, nothing moves on its own whatever the setting: no entry animation or particles, the layout settles at once and zooming jumps. Without WebGL, choosing 3D shows a notice and the graph stays in 2D. If storage is unavailable (private mode) the setting falls back to Automatic.
- **Graph screen: halos by origin** (#95, phase 3). In the force layout, every origin wraps its nodes in a translucent halo of its colour, with its name and count, and a node backed by several origins sits where their halos overlap: each origin has an anchor and a node is pulled to the mean of its origins' anchors; origins that share more nodes are placed next to each other. A **Group by** selector chooses what an origin is (origin type, the default; document; contributor; agent / token; entity type) and redraws the halos without fetching the graph again. The **8 largest** origins get their own halo and the rest are grouped as «Others». The legend lists the origins and **each halo can be turned on or off**, and «Halos by origin» turns them all off. Robustness is visible: a ring on nodes and thicker edges for what is backed by 2 or more origins, an «Only confirmed by 2 or more origins» filter, and the list of origins in the side panel for each node and fact. Nodes without a known origin go to a neutral area below. The graph is now always requested with its provenance (`group_by`), which adds some time in very large brains (see #97).
- **`update.sh`**, attached to every release: backs up, updates and checks in one step (`./update.sh`, `--check`, `--version X`, `--rollback [--with-db]`). It downloads the new image first (a wrong version stops everything before touching anything), keeps **a single backup** (PostgreSQL, documents volume, bundled FalkorDB, `docker-compose.yml` and `.env`) that is replaced only after the new one is complete, adopts the release's compose file only if yours is the unmodified one, and verifies the new version and its health afterwards. See `docs/INSTALL.md`.

- OIDC providers: **initial access** for automatic sign-up (#66). A list of `brain:role` (only `reader` and `contributor`) that a person registered automatically through that provider receives once, when the account is created, as ordinary memberships recorded in the audit log (`member.set`, `via=oidc-default:<provider>`). An administrator can change or remove them and no later sign-in restores them; a group that grants a higher role on the same brain wins. Saving the provider refuses other roles and brains that do not exist. Migration `0022`. See `docs/CONFIGURATION.md`.
- **Provenance in the graph view API** (#95, phase 1). `GET /api/brains/{slug}/graph` takes an optional `group_by` (`label`, `source`, `document`, `author`, `token`). With it, every node and fact carries `sources` (origin keys for that grouping), `source_count` and `provenance` (the keys for every grouping, so a viewer can switch grouping without fetching the graph again), and the response adds `groups`: per grouping, each origin's name and how many nodes and facts it backs. Origins follow the provenance chain: a node comes from the episodes that mention it and from those of its visible facts; an episode gives its type (`text`, `message`, `json`, or `document`, `directory` or `wiki` when it was promoted from a document) and, when it came from a proposal, its author, its API token and the document it was promoted from. Entities without an episode have no origin. Without `group_by` nothing is computed and the response is unchanged: in a large brain the provenance can cost more than the subgraph itself.
- Documentation: how to watch PostgreSQL with an external monitor, since the built-in alerts are stored in it and cannot report its outage (#68). See «Monitoring the instance» in `docs/INSTALL.md`.
- **First steps** screen for a new instance (#77). An administrator who lands on the home page while no brain exists no longer sees «You do not have access to any brain yet. Ask an administrator to add you.»: they get a **Create your first brain** button, which opens the dialog under Administration, and a short checklist (AI models, API token, connecting an agent) with links to each screen. Other people keep the previous message.
- Documentation for a first installation on an empty machine: what to install before starting (`curl`, Docker with Compose v2) and how to prepare Ollama, including making it reachable from the container on Linux (#72); a quick start step to connect the first agent over MCP (#75); and which extraction model to choose, what to expect from small models and that the extraction and embeddings models are independent (#74). See `README.md`, «Before you start» in `docs/INSTALL.md` and «Choosing the extraction model» in `docs/CONFIGURATION.md`.

### Changed
- **Graph screen: calmer focus and motion** (#95, after 0.8.0-rc.1). Hovering a node only focuses it after 250 ms, so crossing nodes on the way changes nothing, and the dimming of the rest fades in and out over about 350 ms instead of switching in one frame (WCAG 2.3.1 and 2.3.3). Particles move three times slower and are smaller and fainter. With **Reduced** effects or with reduced motion in the system, hovering no longer dims anything; only the selected node does.
- Graph screen: **a dragged node stays where it is dropped**, in 2D and 3D, marked with a dot; a double click releases it and the new **Reset positions** button releases them all and lays the graph out again.
- Graph screen: node size grows with the square root of the degree, from 5 to 12, so the most connected node is at most about 2.4 times the smallest one. In 3D, edges are fainter (more so above 150 visible edges), relation names are shown only for the focused or selected node, and halos are less opaque.
- **Graph screen: own 2D renderer** (#95, phase 2). The force layout in 2D is now drawn on a canvas of our own with d3-force instead of `@falkordb/canvas`, as the base for the provenance halos and animations of the next phases. It keeps everything the previous viewer did: search, seeds, hops, minimum degree, right click to expand and undo, legends that hide types and relations without moving the graph, the relation type on every edge, dashed invalidated facts, time travel, the side panel, JSON and image export, pause, and arriving from Knowledge with `?nodo=` (now also zooms to that entity). Initial positions are deterministic, so reloading does not reshuffle the graph; a new graph settles before it is shown and an expansion grows animated from the expanded node. Radial, tree and 3D still use the previous viewer until phase 5.
- Graph screen: «Time travel» no longer fetches the graph in an endless loop in a brain without episodes (for example, one with imported facts only). The start of the timeline was recomputed from the current time on every render, so the requested date changed constantly.
- **The API and the MCP server answer in the caller's language** (#80). Error messages (`detail`), the MCP tool titles, descriptions and instructions, JSON-RPC errors and the headings of the recall context (`## Current facts`, `(since …)`…) follow, in this order, the `Accept-Language` header, the language the session's or token's owner chose in My account and the instance default (`MIMIRSYNTH_DEFAULT_LANGUAGE`). Before, they were always in Spanish, even on an English instance. Stored memory is not translated. The web interface sends its active language, so its messages do not change. Clients that compared error texts with the Spanish ones should send `Accept-Language: es` or compare the status code. See «Language» in `docs/AGENTS.md`.
- `GET /api/brains/{slug}/proposals` is now paginated (#88). It takes `q` (title), `author` (user id), `sort` (`name`, `author`, `conf`, `at`), `order`, `limit` (default 50) and `offset`, and returns `{total, limit, offset, authors, items}` instead of a bare list. Before, it returned at most the latest 200 proposals with no way to reach older ones.
- **OIDC with «Accept unverified emails»** (#66): an unverified email now links only to an invitation, never to an account that is already active. That person sees a message asking them to sign in as usual and link the provider from My account → Security (`auth_error=link_required`). Before, an unverified email matching an active account, including an administrator's, was enough to sign in as that account. With a verified email nothing changes.
- **OIDC: the emails listed as instance administrators** (Administration → Identity) now need an email the provider marks as verified to create their account. Before, with «Accept unverified emails», an unverified email on that list was enough to create an instance administrator.
- `GET /api/health` now also checks PostgreSQL (#68). It returns `db` and `graph` (`true`/`false`) and answers `503` with the same body when either is down, so an external monitor can tell «application down» (no answer) from «application alive, database down». Each check waits at most 2 seconds. The error detail is no longer part of the response (the endpoint is public): it goes to the log.
- The health check of the graph and the AI models now alerts only after **2 consecutive failures** (new setting «Consecutive failures before alerting» under Administration → Notifications; 1 restores the old behaviour). A one-off 500 or timeout from a provider no longer raises an alert and its recovery message.
- The type corrector no longer assumes an infrastructure domain (#56). What it reviews comes from the brain's ontology: entities without a type, entities whose type is not in the ontology, and the types the package lists in its new `retype` block. It used to review only a fixed list (`Person`, `Location`, `Organization`, `Event`…), so in a family brain it checked correct people and places and never looked at pets or belongings. The technical rules that set names aside as doubtful before asking the decider (file, option, code, version, problem) now apply only when the package enables them: all of them in `infrastructure`, which behaves as before; only `option` in `software-knowledge`; none in the other packages or in hand-written ontologies. The decider's question no longer rules out errors or procedures when the ontology has types for them. See `docs/ONTOLOGY.md`.
- **Effect on existing suggestions:** in brains whose package no longer enables a rule, suggestions that the corrector showed as doubtful for that rule (for example «Receta 1.5» for the version rule) are shown as pending again and can be applied. Nothing changes in `infrastructure` brains.

### Fixed
- Graph screen: **Only confirmed by 2 or more origins** hid every relation, since a fact almost never has two origins of its own. It now filters nodes only and keeps the relations between the nodes left; the ones backed by several origins are still drawn thicker.
- Graph screen: the legend uses the full height of the canvas and no longer shows a horizontal scroll bar; long names end in an ellipsis and show in full on hover.
- Graph screen: two halos with the same top (for instance two origins backing the same nodes, which is what «Only confirmed» leaves) drew their names on top of each other; the second one now goes above the first. A selected node hidden by a filter no longer dims the whole graph as if it were the focus. Changing the grouping or turning a halo on or off refits the view, since the nodes move.
- Proposals: with a long list (for example «All» with dozens of rows) the form for new proposals was squeezed down to its first label and could not be used (#88). Only the table scrolls now, and it has a pager; the title and author filters and the sort order apply to every proposal, not only to the rows loaded. Page layouts in general no longer squeeze what sits above a scrolling area.
- `docker-compose.yml`: on Linux, the default embeddings address `http://host.docker.internal:11434/v1` did not resolve inside the container (#73). The `mimirsynth` service now maps that name to the host (`extra_hosts: host-gateway`), as Docker Desktop already did. If you keep your own compose file, add those two lines yourself.
- `GET /api/embedding-engines/reindex` no longer reports `orphan: true` when the shadow fill has finished and is waiting for the switch (#69). `orphan` is now `true` only for a failed or abandoned fill. The `reindex.orphan` alert and the panel already looked at the state, so nothing else changes.
- Markdown documents saved with Windows line endings (CRLF), as Obsidian does on Windows, kept their YAML frontmatter and `^block` marks in the indexed text and lost the `title:` from the frontmatter (#83). Line endings are now normalised before the Markdown conventions are applied.
- Documentation: after changing the embedding model, what to do with `MIMIRSYNTH_EMBEDDING_DIM` and the other `MIMIRSYNTH_EMBEDDING_*` variables in `.env`.
- Administration → AI models: **Check** did nothing visible when the LLM or the embeddings came from `MIMIRSYNTH_LLM_*` / `MIMIRSYNTH_EMBEDDING_*` (#78). It now tests them too, in parallel, and keeps the result next to the button until the next check: model and latency, or the error, and the time. `GET /api/ai-status?check=true` returns `model` and `ms` for each engine it tests.
- Proposals: the **All** counter counted every proposal twice (#79).
- Password fields show every rule (minimum length, not your email or name, not common or a sequence, at least 5 different characters) and tick them while you type, and a disabled submit button says what is missing (#76). This applies to the first-run wizard, invitations and resets, the temporary password screen and My account → Security. The temporary password screen also used a fixed minimum of 12 instead of the configured one.
- Password policy: sequences that wrap around, such as `987654321098` or `…yzab…`, are now rejected (#91). With the default minimum of 12 characters no digit sequence was ever caught, because a 12-digit run always wraps.

## [0.7.1] - 2026-10-27
### Added
- Administration → Embeddings: change the embedding model from the interface (#48). **Reindex** on an engine with another model shows the estimate (items, engine calls, memory) and computes the vectors in shadow; a panel shows the progress with Cancel, unfinished shadows with Retry and Discard and, when ready, **Switch to the new model**, which requires ticking that FalkorDB and PostgreSQL have been backed up. When it finishes it reminds you to recalibrate the recall's minimum passage similarity and to switch agents that write directly to Graphiti.
- Second step of the embedding model change (#48): swapping to the new engine. `POST /api/embedding-engines/reindex/switch` (needs a finished shadow fill and an explicit backup confirmation, kept in the log and the audit) catches up with what changed, pauses vector writes for at most a configurable wait (if writes in progress do not finish, the change is postponed, never the writes), swaps the vectors of every graph and, in one PostgreSQL transaction, replaces the columns and HNSW indexes and makes the new engine the default. On failure the graphs roll back and everything stays on the previous engine; after a crash in the middle, the service makes every graph consistent with the default engine on start, before serving. The pause duration is logged. Interface in a later step.
- First step towards changing the embedding model (#48): a resumable background job computes, with the new engine and without touching the vectors in use, every vector of every brain in shadow (entity and fact embeddings in FalkorDB, `episode_chunks` and `doc_chunks` in pgvector with their own HNSW index). API only for now: a bounded estimate (cheap counts and a sample, with a time limit and a short cache), start (the job estimates and refuses to go on without enough free memory in FalkorDB), progress, cancel, retry and discard. Unfinished shadows leave a marker reported by the API and raise the new `reindex.orphan` alert if they stay failed or stalled. The shadow HNSW index is built concurrently and table changes use a short `lock_timeout` with retries. Batch size and pause between batches are configurable and `Retry-After` is honoured on 429. Cancelling or discarding removes every shadow property, column and index. Swapping the vectors and the interface will come in later steps. See `docs/CONFIGURATION.md`.
- Knowledge → document viewer: under «Mentioned entities», a new **Relations** section shows how those entities relate in the graph («A —relation→ B», with the fact and the date it holds from). Only current facts by default, with a switch to include the ones that are no longer true, and «Show more». One graph query, no LLM or embeddings; `GET /docs/{id}/entities` now also returns `relations`, `total` and `expired_count`.

### Changed
- The decider no longer assumes an infrastructure domain. Triage used to ask whether a proposal was "a factual statement about the infrastructure"; it now judges it against the brain's scope (its description and the entity and relation types of its ontology), and without either only checks that it is factual. The type corrector's questions are generic too. It still never rejects on its own: what does not fit goes to a curator. The brain description can now be edited when creating or editing a brain.

### Fixed
- Knowledge → document viewer: the status tags (indexed, size, chunks) no longer sit flush against the panel header.

## [0.7.0] - 2026-10-26
### Added
- **Notifications**: a bell in the sidebar with the alerts you can see (instance administrators see all; curators see their brains') and, for administrators, channels to send them to: **Telegram**, **ntfy**, **Gotify**, **webhook** (optionally signed with HMAC-SHA256) and **email**. Events: AI model or graph not responding, failed ingestion after its retries, failed job, document source error, account lockout, and new versions (opt-in). Repeated problems are grouped, recoveries are announced, channels filter by severity and event, quiet hours hold non-critical alerts, and failed deliveries retry with growing waits and can be retried by hand. Alerts never include memory content. Channel secrets are stored encrypted; links to the cloud metadata address are always refused. Migration `0021`. See `docs/NOTIFICATIONS.md`.
- **Passkeys (WebAuthn)**: add them in My account → Security and sign in with your device's fingerprint, face or PIN, or use them as the second step after the password. They require user verification, so a passkey counts as two-factor, also when the administrator makes two-factor mandatory. Only the public key is stored; the sign counter detects cloned keys; challenges are single-use. Removing one asks for the password and never leaves an account without a way in; an administrator's two-factor reset also removes the person's passkeys. New dependency `webauthn` and migration `0020`. Needs `MIMIRSYNTH_PUBLIC_URL` over HTTPS. See `docs/CONFIGURATION.md`.
- **Federation between brains**: an administrator of a brain can lend read access to another brain (scope: graph, documents or both; optional expiry; revocable at any time; audited). The receiving brain's `recall` (REST and MCP) merges what it is lent with its own using weighted RRF and marks each lent item with its origin. One way and one hop; no embeddings or summaries are shared. New Administration → Brains → Federation panel, `/api/brains/{slug}/grants`, `federated` option on `recall`, and migration `0019`. See `docs/FEDERATION.md`.
- Wiki adapters for **Confluence** (Cloud and Data Center) and **Notion**, read-only. Written against each API's documented format and covered by tests with simulated responses; not yet validated against a live instance. Docmost is left out for now (no documented public API).
- Knowledge → Sources → Edit: change which collections (spaces, databases) of a connected wiki are indexed, using the stored credentials.

### Changed
- Sign out is now one click away: the sidebar shows the person's avatar and name (linking to My account) with a sign-out button next to it, and My account has a highlighted «Sign out» button under its section menu. It used to be a small button in My account → Security → Sessions.
- A wiki page's content can now be fetched lazily: a rescan only downloads the pages that are new or whose modification date changed.
- Accessibility pass (see `docs/ACCESSIBILITY.md`): every screen has a level-one heading and the sign-in and setup screens a `main` landmark; action columns in tables have a visually hidden header instead of an empty one; the pager no longer overflows at 320 px; a skipped heading level fixed.

## [0.6.0] - 2026-10-26
### Added
- Own MCP server: `POST /api/brains/{slug}/mcp` (Streamable HTTP, stateless) exposes the tools `recall` (reader) and `remember` (contributor) with the same API tokens and roles as the REST API. Only API tokens are accepted, browser origins other than the instance's are rejected, and tool failures are returned to the model as tool errors. See `docs/AGENTS.md`.
- Standard ontology packages replace the old starter ones: `general`, `infrastructure` (rewritten), `team-projects`, `personal-family` and `software-knowledge`. Aligned with schema.org, FOAF, Dublin Core, DOAP and ITIL/CMDB; every type says what it is, when to use it and when not to, with examples; every package has extraction instructions. See `docs/ONTOLOGY.md`.
- Ontology packages are versioned. A brain remembers the package and version it applied; when a newer version ships, **Update** adds what is missing (types, relations, rules) without touching anything you changed by hand. «Replace ontology» now asks for confirmation.
- Tests check each package: valid map, no unused types or relations, descriptions with guidance and examples, no personal data.

### Changed
- The `generic` package is now `general` (the old name still works as an alias).
- Type corrector: applying or rejecting in bulk now asks for confirmation with a summary by proposed type, there is a «Reject all visible» action, the result of each action is reported (including how many did not fit the ontology), the confidence is shown as a percentage and a filter can no longer apply rows it has hidden.
- The request limiter (sign-in, two-factor, password recovery and setup) now keeps its attempts in the database (migration `0018`): it is shared between processes and survives restarts, so restarting the service no longer resets the counters. If the database fails it falls back to an in-memory counter, so access is never left unprotected.
